# Threat model

askdare puts a public, anonymous chat endpoint on the internet that spends money on your OpenAI account and renders model output inside other people's websites. This document lists what we protect, how, and what remains your responsibility. The decisions behind it are in [ADR-0004](docs/adr/0004-threat-model.md).

**Guiding principle:** an anonymous public bot cannot be made unforgeable. A determined attacker can always use it as a rate-limited LLM. We **bound the damage** (requests, tokens and money per day) and **prevent escalation** (data access, script execution, data exfiltration).

## Assets

| Asset | Why it matters |
|---|---|
| OpenAI spend | Every message costs money; abuse turns into an invoice |
| Conversations | May contain personal data typed by visitors; kept at OpenAI by default, or in your own store (ADR-0024), and in transcripts you keep |
| Host pages | The widget runs on your clients' sites; it must not become an XSS vector |
| `OPENAI_API_KEY`, `CHAT_SECRET` | Full API access and the ability to mint session tokens |
| Visitor privacy | Tracking or leaking data across sites |

## Trust boundaries

```
host page ──(script tag)──▶ loader (shadow DOM, host origin)
    │                            │ MessagePort, explicit target origin
    ▼                            ▼
iframe app (your app origin, strict CSP) ──JSON + Bearer, same-origin──▶ askdare route handler
                                                                             │
                                          OpenAI Responses / Conversations ◀─┤
                                          optional shared store (Upstash) ◀──┤
                                          optional turn log (Upstash) ◀──────┤
                                          optional own store (Postgres) ◀────┘
```

Everything to the left of the route handler is untrusted: the host page, the iframe's storage, the request body, and model output. So is the text of your knowledge documents, as the model reads it.

## Threats and controls

| # | Threat | Controls | Residual risk |
|---|---|---|---|
| T1 | **Cost abuse** (OWASP LLM10) | New sessions and conversations per IP; messages per visitor and per IP; turns per conversation; `max_output_tokens`; turn deadline; daily token budgets per bot, per IP and optionally global, **reserved atomically before each turn** and replaced by real usage when it ends; a turn whose model call has started finishes even if the visitor disconnects, so disconnecting saves nothing (an aborted response can't be looked up, usage included); only the server's deadline cuts a turn short, and that keeps the reservation charged; `ASKDARE_DISABLED` kill switch; **hard spend limit on the OpenAI project** | An attacker rotating many IPs (or IPv6 /64s) can spend up to the bot's daily budget |
| T2 | **Reading someone else's conversation** (IDOR) | Conversation IDs never reach clients; resume tokens are encrypted (JWE), bound to bot and visitor; mismatches answer `404` | — |
| T3 | **Forged or stolen session tokens** | JWE with issuer, audience, type, expiry and required claims; keys looked up by `kid` with no fallback; claim formats validated; 15-minute access tokens kept in memory; key rotation with `CHAT_SECRET_PREVIOUS`; short or low-entropy secrets refused | Script running on your app origin could read the resume token from storage (the strict CSP keeps foreign script out). Anyone with physical access to a browser holding a resume token can continue that conversation, and ask the model to repeat it, for up to 30 days. An access token can be renewed up to 1 hour after it expires (so a visitor keeps their uploaded files), within the per-visitor session limit |
| T4 | **XSS through model output** (LLM05) | Markdown without raw HTML; links limited to http(s)/mailto; strict CSP on the iframe (`script-src 'self'`, no inline script); host page never receives model output | — |
| T5 | **Data exfiltration through links and images** (LLM01, LLM02) | Images are never loaded (alt text only); links open with `rel="noopener noreferrer nofollow"` | A visitor can still click a link the model was tricked into writing |
| T6 | **Prompt injection** (LLM01) | Instructions, model and tools are server-side only; clients can't send system messages; page context from `askdare('configure')` is off unless a bot opts in, capped at 1000 characters, normalized, and sent as a marked part of the visitor's own turn (user role), never in the instructions; with `toolResults: 'untrusted'` (opt-in, ADR-0022), tool results reach the model wrapped as third-party data it must not follow as instructions | The model can be talked off-topic; don't connect tools with side effects to an anonymous bot (not supported yet) |
| T7 | **System prompt leakage** (LLM07) | Documented rule: instructions contain no secrets | Assume visitors can extract the instructions |
| T8 | **Unauthorized embedding and clickjacking** | `Content-Security-Policy: frame-ancestors` per bot from `security.allowedOrigins`; no wildcards | `frame-ancestors` stops browsers, not scripts calling the API directly (see T1) |
| T9 | **postMessage spoofing** | Loader sends the handshake to an explicit origin and transfers a private `MessagePort`; the iframe accepts it only from its parent and allowed origins. A page that asks again (`askdare:hello`, ADR-0018) addresses only the allowed origins, and the loader answers only its own iframe on the app's origin | — |
| T25 | **The site's own page in the iframe** (`embedPath`, ADR-0018) | The chat route redirects only to a path of the same app, set in the bot's server config, with only the language and the mode; `embedPageHeaders` gives the page askdare's `frame-ancestors` and microphone rule, and `doctor` fails a page without them, with a wider `frame-ancestors`, without `EmbedRoot` or behind a redirect; the docs give the page a root layout of its own | The page runs the app's code with the chat's origin and only the app's own CSP: its scripts can read the visitor's session, as in the chat inside a page (T23). Opt-in per bot; askdare's own page stays the default |
| T10 | **Cross-site requests and CSRF** | No cookies; Bearer tokens; JSON bodies, and uploads with custom headers, both need a CORS preflight we never grant; advisory `Origin`/`Host` and `Sec-Fetch-Site` checks; request bodies capped at 256 KB while streaming | Non-browser clients can still call the API, bounded by T1 controls |
| T11 | **Excessive agency** (LLM06) | Tools run on the server only, with Zod-validated arguments, timeouts, an output size cap and verified context (bot, visitor, locale); the model never chooses identifiers the tool trusts; a tool's result never reaches the browser, only what its `replies` and `ui` functions pick from it, as plain text options or plain JSON of at most 8 KB, re-derived from the stored result on reload (ADR-0015, ADR-0017) | Don't give an anonymous bot tools with side effects (not supported yet); whatever a tool's `ui` returns, the visitor can read |
| T12 | **Secrets or content in logs** (LLM02) | Message content is never logged; client errors use stable codes without internals; `onUsage` and `onFeedback` reports carry pseudonyms and counts, never message text (only a rating's comment, which the visitor wrote for you) | Your own logging and hosting provider |
| T13 | **Rate-limit evasion with spoofed IPs** | Client IP read according to `trustProxy` (Vercel, Heroku or proxy count), never the spoofable leftmost `X-Forwarded-For` entry; addresses validated; IPv6 grouped by /64 | If `next start` is reachable without a proxy in front, the client controls `X-Forwarded-For` — always deploy behind a proxy that sets it |
| T14 | **Abuse attributed to your organization** | `safety_identifier` (hashed visitor ID) sent with every request, so OpenAI can act on the end user | — |
| T16 | **Malicious or oversized uploads** | Off by default; the type is detected from the file's bytes (PNG, JPEG, WebP, non-animated GIF, PDF; SVG and everything else refused); size capped while streaming (default 4 MB); uploads per visitor and per IP per hour; the widget re-encodes images, dropping EXIF and GPS data; file names sanitized; files are never served back to browsers; PDF pages counted from the file, object streams included, and capped (`maxPdfPages`), with unreadable structure charged at the cap; file tokens reserved for every model call the turn may make; a bot-wide daily upload cap | A PDF or image can still carry prompt injection (T6). A turn cut short by the server deadline stays charged at its reservation, so a PDF crafted to hide pages from the counter but not from OpenAI could then cost more than reserved; the project's hard spend limit bounds this |
| T17 | **Using someone else's files** (IDOR) | OpenAI file IDs never reach clients; uploads return encrypted handles bound to bot and visitor that expire after 1 hour; raw file IDs and foreign handles are refused | — |
| T18 | **Retention of uploaded files** | Files expire after 30 days (`expires_after`) and are deleted with the conversation | Files uploaded but never sent stay until they expire |
| T19 | **Voice input abuse** | Off by default; the microphone is allowed only in the embed page of a bot with voice (`Permissions-Policy`), and the browser asks the visitor; recordings are checked by their bytes (WebM, MP4, WAV, MP3) and capped by size (128 kbps × `maxSeconds`); dictations per visitor per hour; at most 2 per IP and 10 per bot transcribing at once; speech seconds reserved against daily budgets per bot and per IP, then settled with the duration OpenAI bills, or with the longest audio the file could hold when no duration is reported or the call times out; closing the chat or hiding the tab stops a dictation and releases the microphone, and recording stops by itself at `maxSeconds`; the transcript only fills the message field; askdare stores no audio | A low-bitrate recording can hold more than `maxSeconds` of audio. Its real duration is charged after the fact, so the in-flight recordings can exceed a day's speech budget once, before it blocks further dictation |
| T20 | **Injection through widget configuration** | Theme values are validated before they are written into the theme stylesheet (hex colors, CSS values without `url()`, quotes, braces, semicolons or backslashes, so nothing can point to another origin; font-family characters only); variant attributes are fixed enums and HTML-escaped; the requested bot's launcher look replaces the quoted placeholder in `widget.js?bot=` as a JSON string literal (safe for any content, tested against the built loader), and no other bot's look is included; the avatar is a same-origin path or a raster data URL (no SVG, no other origins); `widget.css` is the developer's own CSS, loaded under the iframe's CSP (no external images, fonts or imports); `askdare('configure')` accepts only a greeting, suggestions and page context, checked again in the iframe and on the server; the state gallery is off unless `createChatHandler({ gallery: true })` | A bot's public launcher look (colors, label, avatar path) is visible to anyone who loads its `widget.js` |
| T21 | **Probing the setup through `askdare doctor`** | `POST /doctor` answers only to a 2-minute token encrypted with `CHAT_SECRET`, with its own type and audience, so session tokens don't work; the CLI sends it only over https (plain http to localhost) and never follows redirects; one run at a time per instance and 3 a minute across the app, and the kill switch stops it; the report holds statuses, model and vector store IDs and fixed messages, never keys or OpenAI's error text; the test conversation and file are deleted at once, and the test response isn't stored | Whoever knows `CHAT_SECRET` can start 3 runs a minute, each a few small OpenAI requests per bot (a 16-token response, one second of transcription) |
| T22 | **Impersonating a signed-in user** (`askdare('identify')`) | Identity comes only from an HS256 JWT signed with `IDENTITY_SECRET` (at least 32 characters, different from `CHAT_SECRET`), with the bot as audience and at most 24 hours between `iat` and `exp`; `configure()` and the model can't set it; `iat` may not be in the future; the token is checked again at every session request, and access tokens expire with it; a refused or missing token leaves the visitor anonymous, and a failed sign-out leaves no usable session; names lose line breaks and control characters; conversations started while signed in, or adopted at sign-in, are bound to an HMAC of the user and hidden from anyone else on the same browser; `safety_identifier` hashes the user ID | A leaked token works for its holder until `exp`; whoever has `IDENTITY_SECRET` can sign in as anyone; sign-out on the site needs `identify(null)`; a user's display name in instructions is their own text |
| T15 | **Supply-chain compromise** | Dependency install scripts blocked by default; one-day minimum release age; GitHub Actions pinned to SHAs; npm provenance via trusted publishing; reviewed and pinned agent skills | A compromised direct dependency that passes review |
| T23 | **The chat inside a page** (`@boldare/askdare/react`, ADR-0011): no iframe between the page and the chat | Same origin only: `Root` refuses a `basePath` or stylesheet URL that isn't a path of the chat route, and the route's same-origin check is unchanged, so there is no CORS; model output becomes React elements, never HTML (the XSS payloads run against the published build, and the build is checked for HTML sinks); citation and Markdown links are limited to http(s)/mailto; `getChatConfig` returns only the public configuration (tested for secrets); the bot's theme and its own CSS are scoped to that bot's chat | The page's scripts can read the conversation, the session tokens in memory and the resume token in storage, and its Content Security Policy is the only one: on pages with untrusted scripts, use the iframe widget. A page that passes `identity` puts the token in its HTML and must not be cached |
| T24 | **Forged or foreign answer ratings** (`POST /feedback`, ADR-0012) | Each answer carries an encrypted rating handle, bound to the bot and to the visitor or signed-in user, so only they can rate it; the request needs a session's access token; 20 ratings a minute per visitor; comments are capped at 500 characters; askdare stores no ratings, and the OpenAI conversation and answer IDs reach only `onFeedback`, never the browser | A visitor can rate their own answers as often as the limit allows; a comment is untrusted text that the app must escape wherever it shows it |
| T26 | **Bypassing the human check** (`security.humanVerifier`, ADR-0023), opt-in | The Turnstile token is checked with Cloudflare's siteverify on the server, after the session rate limit, with a 10 s timeout; a token that fails, expired or was used before answers `unauthorized`; the server refuses a token whose `action` isn't the bot's id, so a token solved for another bot or widget on the same site key doesn't count, and `hostnames` can pin where it was solved; the check **fails closed** when Cloudflare can't be reached or rejects the secret key; the browser receives only the site key; **renewals are capped**: the access token carries when the check was passed (`hv` claim), a renewal keeps that time, so renewing never extends it past 24 hours, and tokens without the claim count as unchecked | Turnstile raises the cost of automation; it doesn't stop a person, or a solving service, from passing a check and then using one session for up to 24 hours within the T1 limits. Cloudflare's `api.js` runs with the chat origin's access (the iframe, or your page for a chat inside it) and has no Subresource Integrity, so turning the check on means trusting Cloudflare with the conversation on screen and the resume token. Cloudflare's test secret keys skip the `action` and hostname checks |
| T27 | **Guardrails that fail or are worked around** (`moderation`, `onInput`, `onOutput`, ADR-0022), opt-in | Checks run on the server before the model reads a message and before an answer leaves the server; while answers are checked, the server holds them back until complete and checked, so a blocked answer never reaches the browser, and a replaced one goes out without the tool cards, reply options and rating handle `onOutput` didn't see; nothing blocked or redacted is logged as content. **Fail open:** a hook that throws or returns a malformed verdict, and a moderation call that fails, let the text through and log one line without content, so a guardrail outage never breaks the chat. **Notes can't be forged:** for bots with output checks, history shows an answer only once a fixed developer note settles it (`[askdare:allowed]`, `[askdare:withheld]`, `[askdare:replaced]`); only developer items with that exact text count, which visitors and the model can't write, and a replacement is stored as an assistant message, never with developer authority. **Conversation lock:** such a bot takes one turn at a time per conversation, with a hold in the rate-limit store for `turnTimeoutMs` plus a minute, so concurrent turns can't settle each other's answers; a second turn gets `rate_limited` | Fail open means a moderation outage, or a buggy hook, lets messages and answers through unchecked. Attached files aren't checked. The original of a withheld answer stays in the OpenAI conversation until it is deleted, and if its note can't be written the answer stays hidden in the history. With the in-memory store the lock is per instance, like every limit. Guardrails reduce harmful content; they are no defence against prompt injection on their own (T6) |
| T28 | **Paging someone else's history** (`POST /history` with `before`, ADR-0024) | The `before` cursor is opaque: encrypted with `CHAT_SECRET` (JWE) under its own type, with the bot as audience and the conversation inside, and valid as long as a resume token; the conversation is still taken only from the resume token, which must belong to the session's visitor or signed-in user, and the store must list it as theirs (`info()`); a cursor from another conversation, even the same visitor's, answers `400` before anything is read; history reads stay at 20 a minute per visitor | — |
| T29 | **Resuming someone else's answer** (`POST /resume`, ADR-0027) | The answer is found only from the conversation in the verified resume token, never from the request alone: its log key is an HMAC (a key derived from `CHAT_SECRET`) of the bot, that conversation and the answer's `messageId`, so a `messageId` from another conversation finds nothing; the resume token must belong to the access token's visitor or signed-in user, and the store must still list the conversation as theirs (`info()`); unknown, expired and foreign answers all answer `404` alike; 30 resumes a minute per visitor, and a resumed stream ends at the bot's turn timeout; the resume tokens a turn logged name whoever started it, so a resumed stream replaces them with one issued for the session that resumes: a visitor who signed in during the answer gets their own, never the anonymous one that would outlive their sign-out; on a live stream, the chat client keeps a token only while the session that sent the message is still the one in use, so a sign-in or sign-out during the answer keeps the handle it gave (or none) | — |
| T30 | **Answer text in the turn log** (ADR-0027) | The log holds what the visitor's chat receives for one answer (its text, sources, cards, reply options, rating handle and resume token), never the visitor's message, instructions, tool arguments or results; with output checks, only an answer that passed them; keys are HMACs, so the log holds no conversation IDs, visitor IDs or IP addresses; each answer expires after the bot's turn timeout plus 1 minute, counted from its last batch; askdare logs nothing of what it holds, and a failure by the error's class name only; in the server's memory by default, in your own Upstash database with `upstashTurnLog()` | For those few minutes, whoever can read the Redis database can read the answers being written: it is personal data, for your privacy notice ([Privacy](docs/privacy.md#turn-log)) |
| T31 | **Another visitor's or bot's conversation in your own store** (`conversations`, ADR-0024) | Every request that reads, continues, resumes or deletes a conversation checks the store's own record through `info()`: its bot and its owner (the visitor, or an HMAC of the signed-in user) must match the session, and a mismatch answers `404` like an unknown conversation; conversation IDs are made by the server and never reach clients; `@boldare/askdare-postgres` sends every value from a request as a bound parameter, and the `indexId` it writes into a vector index's DDL (which takes no parameters) is checked against a pattern without quotes, then quoted anyway; askdare never changes the schema while it serves (`migrate` does), so the app's database user needs only `select`, `insert`, `update` and `delete` | Whoever can read the database reads every conversation in clear text: restrict access, choose the region, and sweep old conversations ([Own your data](docs/own-your-data.md#8-sweep-old-conversations)) |
| T32 | **Poisoned or leaking knowledge** (`search_knowledge`, ADR-0025) | Results always reach the model inside ADR-0019's untrusted-data wrapper, JSON-encoded so no document text can close it, whatever `toolResults` says, with a rule never to follow instructions inside them; queries are capped at 1,000 characters, results at 32,000 characters, a search at 15 s; a citation carries only the document's title and an http(s) URL, never its text, and the model cites result IDs it received, never URLs; each index is isolated by its `indexId`, every query is filtered by it, and a bot searches only the index its server config names | Whoever can change the synced folder or the database decides what the bot reads and links to; a document can still sway the model (T6) |
| T33 | **Transcripts leaking from `onTranscript`** (ADR-0016), opt-in | The only hook that receives message content: the visitor's message after `onInput` and the answer they saw after output checks, never instructions, page context, tool calls or results; askdare hands it to the developer and keeps and logs none of it; a hook that throws is reported to `onError` as `internal_error` with the error's class name only, never its message, which could quote the values | Where transcripts go, who reads them and how long they stay is the app's to decide; they outlive a deleted conversation (open notes below) |
| T34 | **Compaction** (`limits.compactAt`, ADR-0029), opt-in | The compaction request reuses the turn's settings: the bot's model, instructions, tools and `safety_identifier`, with `store: false`, a fixed output cap and a 60 s timeout, and its tokens are reserved against the same daily budgets first, or it is skipped; it appends one encrypted item and rewrites nothing stored, so history, paging, ratings and deletion read the original items; when the visitor writes meanwhile, the compaction is dropped | The summary is OpenAI's and opaque: askdare can't check what it keeps, so an injected instruction from earlier turns may survive in it |

A browser extension or script on the app origin can read the page |
| T36 | **Server configuration and stored conversations shown in a browser** | The configuration view is built from an allowlist of fields of the resolved bot, so keys, secrets and environment values never reach it, and new fields stay hidden until listed; raw conversation IDs never reach the browser, only sealed references bound to the admin session; the page and API answers are `no-store`, `noindex`, `Referrer-Policy: no-referrer`, with a CSP of `default-src 'none'`, `script-src 'self'`, `frame-ancestors 'none'` (no framing, no inline script); JSON `POST` with Bearer only, no CORS; transcripts and comments are rendered as text, never HTML | Instructions are visible to every owner (they hold no secrets, T7). An owner's screen shows visitors' messages when transcripts are on |
| T37 | **Playground turns as a spending path** | They run through the normal turn path, under the bot's limits and daily budgets, and appear in `onUsage` and the admin store marked as console turns; their conversations belong to an `admin:` owner no visitor can resume | An owner can spend up to the bot's budgets, as a visitor can |
| T38 | **Admin records outliving their conversation** | Core writes the records itself, so a store set for writes is always the one deletes reach; `DELETE /conversation` deletes the admin records first, then the conversation, so a failure can be retried; `sweep()` deletes swept conversations' records and files, then the admin store's records older than `retentionDays` (default 30); records carry pseudonyms, never raw visitor IDs, identities or IP addresses; stores log nothing of what they write; `doctor` warns when records older than the retention remain | Nothing is swept unless the app calls `sweep()` on a schedule. A turn that ends after its conversation was deleted can still write a record, and a failed admin delete during a store sweep leaves records nothing points at; both wait for retention. Transcripts an app keeps through its own `onTranscript` stay the app's to delete |

## Your responsibilities

The library can't do these for you. [The going-public guide](docs/going-public.md) walks through each one:

1. A **dedicated OpenAI project**: a restricted key, a model allowlist and a **hard spend limit** with alerts.
2. A random `CHAT_SECRET` of at least 32 characters, kept out of git, with a rotation plan.
3. An accurate `security.allowedOrigins` list.
4. A **shared rate-limit store** (`@boldare/askdare-upstash`) when more than one instance serves traffic.
5. The right `trustProxy` setting for your hosting.
6. Instructions with no secrets in them.
7. A privacy notice, a retention decision (conversations stay in OpenAI until deleted, ADR-0003, or in your own store until you sweep them) and an AI disclosure.
8. With your own store or transcripts: a database only the app and its maintainers can reach, and a retention for what it keeps.

## Open notes

Low-confidence findings of the 0.6 security review, still open ([ROADMAP](ROADMAP.md#known-gaps)):

- **Transcripts outlive a deleted conversation.** Deleting one calls no hook, so a transcript kept through `onTranscript` stays until the app sweeps it. 0.7 closes this for transcripts in the admin store (ADR-0032, T38 above, pending c5).
