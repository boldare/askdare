# chatdock — project instructions

`@boldare/chatdock` is a Next.js library for embeddable AI chatbots, built on the official `openai` SDK (Responses API and Conversations API). Status: pre-alpha, local-only until the publication step. Architecture decisions live in `docs/adr/`. Read the relevant ADR before changing anything it covers.

## Repository layout

- `packages/chatdock/` is the core package `@boldare/chatdock`. Add-ons will be `packages/chatdock-*` (`@boldare/chatdock-*`).
- `examples/starter/` is a Next.js app. It is the e2e target, the scaffold source and the docs sample. Once created, it gets its own `CLAUDE.md` that imports the `AGENTS.md` generated by `next dev`.
- `spikes/` holds throwaway experiments. Each spike is standalone and outside the pnpm workspace; never import from it.
- `docs/adr/` holds the Architecture Decision Records.

## Non-negotiable rules

- **OpenAI:**
  - Only `packages/chatdock/src/openai/` may import `openai`.
  - Published `.d.ts` must contain no `openai` or `next` types.
  - Never forward raw OpenAI stream events to clients; use our versioned SSE protocol.
  - Never hardcode model IDs in the library.
  - Before using any OpenAI endpoint or parameter, check the `openaiDeveloperDocs` MCP server. The API changes monthly, and memory is often stale. See the `openai-api` skill.
- **Next.js:**
  - App Router and the Node.js runtime only: no Edge runtime, and `proxy.ts`, never `middleware.ts`.
  - The library must not read the file system at runtime.
- **Security** ([ADR-0004](docs/adr/0004-threat-model.md)):
  - The client never chooses the model, instructions, tools, vector stores, raw `file_id`s or conversation IDs.
  - No cookies.
  - No message content or PII in logs.
  - Sanitize all rendered model output.
- **Public API** ([ADR-0006](docs/adr/0006-support-matrix-and-versioning.md)): the public surface is deliberately small. Anything not listed in ADR-0006 is internal; don't export it.

## Workflow

- **Branches and commits:**
  - Work on a branch `type/short-description`, and merge into `main` with `--no-ff` once the step's Definition of Done is met.
  - Commits follow Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`).
  - Commit locally as work completes. **Never push, create remote repositories or publish to npm without the user's explicit approval.**
- **Changesets:** changes to published packages need a changeset. See the `release` skill.
- **ADRs:** decisions that are expensive to reverse get an ADR. See the `adr` skill.

## Skills and tools

- **Project skills:**
  - `typescript-conventions`: how we write TypeScript.
  - `openai-api`: rules for anything touching OpenAI.
  - `release`: changesets and publishing.
  - `adr`: decision records.
- **Vendored skills** (pinned, see `.claude/skills/sources.json`):
  - `vercel-react-best-practices`: React performance.
  - `vercel-composition-patterns`: compound components for the headless UI.
  - `tsdown`: library bundling.
  - `next-dev-loop`: verifying the starter app at runtime.

  Where a vendored skill conflicts with this file or an ADR, this file and the ADR win.
- **Before merging security-relevant work** (Phases 2–4): run `/security-review` and `/code-review`.
- **MCP servers** in `.mcp.json` are read-only:
  - `openaiDeveloperDocs`: OpenAI docs and the OpenAPI spec.
  - `next-devtools`: errors, routes and logs of a running `next dev`.

  Servers that can write to accounts (Vercel, Heroku, Upstash) stay in user or local scope, never in this repo.
