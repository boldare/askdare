# 3a. History beyond 100 items: paging by turn on the server

- **Status:** blocked (k2, t1)
- **Release:** 0.6 (base branch `release/0.6`)
- **Lane:** Core
- **Touches hot files:** Yes (`protocol/history.ts`, `protocol/schemas.ts`, `docs/protocol.md`, `openai/history.ts`, `server/handler.ts`)
- **Changes the public API or the protocol:** Yes: protocol, additive within v1 (minor changeset)
- **Depends on:** k2 and t1 (they share the history files and `server/handler.ts`; logically only task 1)

## Goal

`POST /history` can page back through a whole conversation, by whole turns, on both kinds of store, instead of stopping at the latest 100 items.

## Decisions to read first

- [ADR-0024](../docs/adr/0024-conversation-store.md) (Proposed), decision 7; ADR-0015 and ADR-0017 (replies and cards per turn), ADR-0022 (settled answers).
- `spikes/s7-store/FINDINGS.md`, question 7 (probe p4).
- The `openai-api` skill: check `conversations.items.list` cursors in the `openaiDeveloperDocs` MCP server.

## Files and area

- `protocol/history.ts`, `protocol/schemas.ts`, `docs/protocol.md`: `before` in the request, a next cursor in the response (absent on the last page). Old clients that send no cursor get the latest page, as today.
- The page is extended back to the visitor message that starts its oldest turn, so cards, replies and settled answers are always read per whole turn.
- `openai/history.ts` (provider store, `items.list` with a cursor) and the item-store reader from task 2 (`page()`). The cursor is opaque to the client and checked against the visitor's conversation, never trusted to name another.
- A page size limit on the server.

## Don't touch

- `chat/*`, `react/headless.ts`, `i18n/texts.ts`: the client side is 3b.
