# h6. The live stream doesn't hand back an anonymous resume token

- **Status:** ready
- **Release:** 0.6.x (base branch `main`)
- **Lane:** Hygiene
- **Touches hot files:** Yes (`chat/store.ts`, if the fix lands there; `chat/chat-client.ts` is not hot)
- **Changes the public API or the protocol:** No
- **Depends on:** none. Lands on `main` before 0.7-c2 starts, since c2 changes `chat/store.ts`; then `main` is merged into `release/0.7`

## Goal

A visitor who signs in while an answer streams, and whose stream doesn't drop, doesn't end up with the anonymous resume token stored in the signed-in user's place. This is the second half of h1 (#192), which fixed `POST /resume` only. `THREAT_MODEL.md` lists it under the open notes (T29), and ROADMAP lists it under "Known gaps".

## Decisions to read first

- [ADR-0027](../docs/adr/0027-stream-resume.md), [ADR-0009](../docs/adr/0009-visitor-identity.md), [ADR-0024](../docs/adr/0024-conversation-store.md) (adopting a conversation at sign-in).
- `THREAT_MODEL.md` T3, T29 and the open note below the table.
- #192: how the server now issues a token for the session that resumes.

## Files and area

- `packages/askdare/src/chat/chat-client.ts`: where the stream's `resumeToken` is stored (`storage` under `#resumeKey()`), and how the key depends on the identity.
- `packages/askdare/src/chat/store.ts`: sign-in and sign-out while a turn streams.
- Likely fix: when the identity changed after the turn started, the client keeps the token it got at sign-in (or none) and ignores the one the stream ends with. Check the server side as well (`server/stream-turn.ts`): if the turn can't know about the sign-in, the client is the right place.
- Start with a failing test: an anonymous turn streams, the visitor signs in, the stream ends normally, and the stored token for the signed-in user must not be the anonymous one.

## Don't touch

- `server/handler.ts`, unless the fix needs it (h1 already changed it). The React entry beyond the headless budget: there are 977 B left in the headless case.
