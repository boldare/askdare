# C1. CI that covers what releases check by hand

- **Status:** ready
- **Release:** 0.4.x
- **Lane:** CI
- **Touches hot files:** No
- **Changes the public API or the protocol:** No
- **Depends on:** none

## Goal

What `RELEASING.md` checks by hand, and what only runs on the maintainer's Mac, runs in CI, so a broken starter or a visual regression shows up on the pull request that causes it.

## Decisions to read first

- ADR-0006 (support matrix and guards), ADR-0007 (tooling).
- `RELEASING.md`, section 2 (manual checks).

## Files and area

- **Starter:** `examples/starter` is never built or type-checked in CI (root `pnpm build` filters `./packages/*`). Add a `typecheck` script there and a CI step that builds it against the workspace package.
- **Adopter path:** run `scripts/verify-packs.mjs` (pack, `create-next-app`, `init`, `doctor`, Turbopack and webpack builds, a chat against the mock) in `canary.yml`, nightly.
- **Visual tests:** `e2e/visual.spec.ts-snapshots/` holds only `-darwin` baselines. Generate Linux baselines in the Playwright container CI uses and run the visual project in `ci.yml`.
- **Node 26:** became LTS in October 2026. Add it to the `ci.yml` matrix. Widening `engines` and the support matrix belongs to 0.5 (ADR-0020), so here it is test-only.
- **Canary:** add Firefox and WebKit (the same subset as `ci.yml`) and the pack-and-install path.

## Don't touch

`packages/` source. Model IDs in workflows come from secrets or variables, never inline.

## Definition of Done

- [ ] Starter typecheck and build in `ci.yml`
- [ ] `verify-packs` nightly in `canary.yml`
- [ ] Linux visual baselines committed and the visual project in `ci.yml`
- [ ] Node 26 in the matrix
- [ ] `RELEASING.md` says which manual checks CI now covers
- [ ] CI green on the pull request
