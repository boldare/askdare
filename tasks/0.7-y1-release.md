# y1. Release 0.7

- **Status:** blocked (z1)
- **Release:** 0.7 (base branch `release/0.7`, then `main`)
- **Lane:** Decisions
- **Touches hot files:** No (release steps only; fixes they find become their own branches)
- **Changes the public API or the protocol:** No, unless the maintainer accepts z1's recommended changes (step 3)
- **Depends on:** z1 (every other 0.7 task is merged)

## Goal

0.7 is published to npm as `latest`, after 0.6.1 or with the 0.6.x patches inside it, `@boldare/askdare-admin` published for the first time, and everything the 0.7 tasks left unchecked checked first. Follow [`RELEASING.md`](../RELEASING.md) from top to bottom; this file lists only what is specific to 0.7, so that none of it is forgotten.

## Decisions to read first

- `RELEASING.md` (all sections) and ADR-0006, with the 0.7 surface z1 added.
- ADR-0030 to ADR-0033, each with its "As built in 0.7" section: the release notes describe what was built, not the first draft.
- `ROADMAP.md`, "Ready to release" and "Known gaps": what 0.7 contains and what it knowingly leaves open. Nothing there blocks the release, but the release notes shouldn't promise any of it.

## Steps

### Before merging into `main`

1. **Bring 0.6.1 into `release/0.7`, if it shipped.** The 0.6.x patches' five changesets are on `main` and, since #207 merged `main` into `release/0.7`, on `release/0.7` too: `doctor-store-timeout`, `rating-replaced-answer`, `resume-after-sign-in` and `resume-token-live-stream` (`@boldare/askdare`, patch) and `postgres-compaction-index` (`@boldare/askdare-postgres`, patch). The "Version packages" pull request #191 on `main` releases them as `@boldare/askdare` 0.6.1 and `@boldare/askdare-postgres` 0.1.1, and is likely to merge first. Then:
   - merge `main` into `release/0.7` through a pull request with a merge commit, **before** the 0.7 "Version packages" step. The merge deletes the five changesets #191 consumed (they stay on `release/0.7` otherwise, and 0.7.0 would list them a second time) and brings 0.6.1's versions and `CHANGELOG.md` entries;
   - resolve the conflicts in `package.json` versions and `CHANGELOG.md` files in favour of `main`;
   - check with `pnpm changeset status --verbose` that none of the five is listed any more.

   Whatever else lands on `main` before the release comes the same way.
2. **If 0.6.1 hasn't shipped, the patches go out inside 0.7.0.** Changesets takes the highest bump per package, so the 0.7 "Version packages" pull request releases them inside the minor, under "Patch Changes" in the same `CHANGELOG.md` entry; close #191 unmerged then, so it can't release them a second time. Don't release anything else from `main` while `release/0.7` waits. Either way, the versions are:
   - `@boldare/askdare` 0.7.0, `@boldare/askdare-admin` 0.1.0, `@boldare/askdare-postgres` 0.2.0, `@boldare/askdare-upstash` 0.3.0 (minor);
   - `@boldare/askdare-otel` 0.1.5 (patch, from its dependency on core), as `changeset status` gave on z1's branch.
3. **Settle z1's API recommendations.** z1's pull request lists the changes it recommends but didn't make (removals and renames). The maintainer decides each; whatever is accepted lands on `release/0.7` before this release, with the snapshot regenerated (`pnpm --filter @boldare/askdare api:update`), ADR-0006 and the changesets. After 0.7.0, each costs a deprecation first (ADR-0006).
4. **Read every changeset in `.changeset/` together, as the 0.7 changelog.** Check that each one is accurate against the "As built" sections, describes nothing as "coming later", has the right bump and doesn't duplicate another. Handoff and forms are spread over six changesets (p1, p3, c1, c2, c3, c4) and admin over four (p2, c5, a1 or a2, a3): merge them into a few entries a user can read, and keep each package's own. The h1 and h6 changesets mention each other as separate 0.6.x fixes; they now ship together, so one entry can say it.
5. **Add `@boldare/askdare-admin` to the release tooling.** z1 found it missing:
   - `scripts/release-packages.mjs` lists the packages it releases in `PACKAGES`, and `packages/askdare-admin` isn't there, so "Version packages" would bump it and nothing would publish it;
   - `scripts/verify-packs.mjs` packs and installs the other four packages, not this one: add it, and import `adminDashboard` in its fresh-app check.

   A fix branch into `release/0.7`, with its own pull request.
6. **Run the live checks that no 0.7 task ran.** Each needs a key or a database; spend stays under a dollar.
   - **The Upstash admin store against Upstash itself:** `ASKDARE_TEST_UPSTASH=1` with a real, throwaway Upstash database (the contract sweeps everything before its `epoch` plus 201 days). It passed against a local Redis behind the REST proxy, never against Upstash. Run the turn log's contract in the same go.
   - **The `handoff` and `show_form` tools against the live API:** no smoke test calls them; the e2e tests use the mock. One turn each on the smoke test's cheap model, checking that the strict schemas (the reason enum, the nullable `summary`, the enum of form names) are accepted, and that `allowed_tools` leaves them out on the last step. Add them to `gateway.smoke.ts` if they fit there.
   - **Handoff to a real receiver,** with the maintainer's own settings: `webhookHandoff` to a receiver that verifies Standard Webhooks (e2e covers a local one), and `emailHandoff` through the maintainer's mail provider, checking the `Reply-To` and that the subject carries nothing the visitor typed.
7. **Check admin on Vercel,** with the maintainer's approval for a preview deployment:
   - deploy `release/0.7` with `ADMIN_SECRET` set and an admin store (Upstash's, if the project has KV connected);
   - sign in to `<basePath>/admin` with the secret, then with an identity token (audience `askdare:admin`), and open the configuration, `doctor`, the playground, a conversation review and the dashboard;
   - call `sweep()` from a cron route behind `CRON_SECRET`, as `docs/admin.md` shows, and check its result;
   - delete a conversation from the chat and check that its records are gone from the dashboard.
8. **Check the greeting by hand where e2e can't:** VoiceOver (macOS and iOS) and NVDA read the launcher with "new messages" once an answer arrives while the chat is closed, and the greeting never takes focus; with reduced motion, the greeting appears without its animation.
9. **Work through `RELEASING.md` sections 1–4.** For 0.7 in particular:
   - `README.md`'s packages table lists `@boldare/askdare-admin`, and its features cover handoff, forms, admin and the greeting;
   - `RELEASING.md` section 2 lists `packages/askdare-admin` among the package READMEs, and section 5's existing-package list covers it after this release;
   - the home page mentions 0.7, and the docs navigation lists `handoff`, `forms` and `admin` (d1 added them);
   - Vercel's environment for the site: `ADMIN_SECRET` (as Secret, since it signs into the console; update `RELEASING.md` section 3, which names only `OPENAI_API_KEY` and `CHAT_SECRET`), and `HANDOFF_WEBHOOK_URL` with `HANDOFF_WEBHOOK_SECRET` if the demo should post handoffs;
   - `THREAT_MODEL.md` has the console's section (c5). Check that the console and the handoff and form endpoints had `/security-review` and `/code-review` (RELEASING.md section 1), and that their findings are fixed or written down.

### Publishing

10. **First release of `@boldare/askdare-admin`.** It doesn't exist on npm (it is at 0.0.0 in the repository), so trusted publishing can't create it. As `RELEASING.md` section 5 says, and as `@boldare/askdare-postgres` did on 2026-11-26:
    - publish a placeholder version by hand, with 2FA, from the maintainer's machine (the postgres add-on used `0.0.0-placeholder`, under a dist-tag other than `latest`);
    - on npmjs.com, add the package's trusted publisher: repository `boldare/askdare`, workflow `release.yml`, environment `npm`, with "Allow npm publish" if `NPM_RELEASE_MODE=publish`;
    - do both before "Version packages" merges, or the release of 0.1.0 fails.
11. **Merge `release/0.7` into `main`** through a pull request, then merge the "Version packages" pull request. Auto-merge is off in the repository: both merge by hand.
12. **Check npm:**
    - `@boldare/askdare` 0.7.0, `@boldare/askdare-admin` 0.1.0, `@boldare/askdare-postgres` 0.2.0, `@boldare/askdare-upstash` 0.3.0 and `@boldare/askdare-otel` 0.1.5 are on npm, with provenance, under `latest`; with `NPM_RELEASE_MODE=stage`, approve each staged version first;
    - `npm install @boldare/askdare@latest @boldare/askdare-admin @boldare/askdare-postgres` works in a fresh app;
    - `@boldare/askdare-admin`'s placeholder doesn't hold `latest` (`npm dist-tag ls @boldare/askdare-admin`).

### After

13. **`RELEASING.md` section 7:** the GitHub release, the site's docs, deleted branches, and sharing the news. Say plainly what handoff is in 0.7: one-way, a person answers by email; live chat comes later.
14. **Move 0.7 into "Released"** in `ROADMAP.md`, move what this release fixed out of "Known gaps" (the Upstash contract run, if step 6 ran it), and give 0.8 its task files once it is planned. 0.8 starts with little room in the React entry (538 bytes) and the headless case (86 bytes); its plan should say which feature makes room.

## Don't touch

- Features. A problem the checks find becomes its own fix branch into `release/0.7` (before the merge into `main`) or `main` (after), with its own pull request.
- The repository's settings (auto-merge, rulesets) unless the maintainer changes them.
