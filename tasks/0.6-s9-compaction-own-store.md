# S9. Spike: compaction on a store we own

- **Status:** ready
- **Release:** 0.6 (Spikes lane; ships nothing; feeds a compaction ADR)
- **Lane:** Spikes
- **Touches hot files:** No
- **Changes the public API or the protocol:** No (an experiment only)
- **Depends on:** none

## Goal

A go or no-go, with numbers, for compaction now that askdare can own the stored history, and a Proposed ADR that decides it. S5 and S5b ruled out OpenAI's server-side compaction **inside a conversation** as a default: at 50k tokens it ran on every turn, lost the prompt cache each time (12–24× the cost), added seconds before the first token, and `file_search` answers lost their citations. With an item store (ADR-0024) and own retrieval (ADR-0025) several of those causes may be gone. S7 didn't test compaction, so 0.6 can't decide it yet.

## Questions the spike answers

1. **Is it needed?** With `limits.maxTurns` at its default of 50, how large does a realistic askdare conversation get (tool outputs and search results included)? At what size does cost or latency hurt? If no realistic conversation gets there, the answer is no-go, and the spike can stop early.
2. **Server-side compaction, stateless** (`context_management` with `store: false`): the compaction item comes back as output; store it as a `native` item and start the next replay at it (the `maxItems` window). Does the cache survive between compactions, so the cost hits once per compaction instead of every turn? At what threshold does input shrink (S5b: about 60k recent tokens are kept verbatim)?
3. **The compact endpoint, off the critical path:** compacting after a turn has ended (in `waitUntil`), so the visitor never waits for it. Latency, cost, and what the next turn caches.
4. **Our own summary**, with a small model, as a provider-neutral fallback (S6a and S6b endpoints have no compaction). Quality against S5b's fact-recall checks.
5. **Citations after compaction** with ADR-0025's markers: does the model still cite earlier passages correctly, and do the IDs still resolve?
6. **Budget and usage:** output tokens spent per compaction, and whether `usage` reports them so `limits` budgets stay right.
